# Task B / Task C faction data contract (2026-10-13)

Generated by `tools/spawn-tuner/factions.py` during `build_data.py`:
`data/factions.json` = `{version:1, slots:[role...], factions:[entry...]}`.
The same entries are embedded in `library.json.factions`; the nine roles are `library.json.flavorSlots`.
Entry: `{id, label, group, emblem, available, slots, emptySlots, fallbacks}`.
`group` is good/neutral/sinister. `emblem` is a tuner-relative path (`assets/emblems/<id>.webp`) or null until accepted.
`available` requires an accepted idol. `slots` maps every role to a SKU array (empty array when unfilled).
`emptySlots` explicitly lists those unfilled roles; `fallbacks` maps a slot to `{role, place}`; an empty censer slot reuses `{role:"censer-hanging", place:"ceiling"}` above the altar or before the idol. It is unlit bronze, not a new flame type.
Consumers should show available entries, resolve emblem paths against the tuner asset base, and use a graceful plain button when emblem is null.

IDs: sun, moon, devils, spiders, dragons (label Dragon; one head), skulls, tentacles, nature,
sword-shield, death, scales-coin, forge-hammer, sea-storm.
Set `room.flavor` to the ID. No engine special case per faction. Default pools remain frozen at the original four;
new factions are selected explicitly, never introduced into existing seed rolls.

Task B compatibility: metadata also includes `pieceLabel` and `aliases`. Picker code accepts the embedded faction array. Automatic engine inheritance must filter defaults to sun/moon/devils/spiders before checking available idols; otherwise additional assets silently change existing building rolls. `engine/test/faction-defaults.test.mjs` guards this with 128 buildings per religious family and explicit new-faction overrides.
